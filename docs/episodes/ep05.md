## Episode Outline

### The Problem with "Just Run It Again" (~3 min)
The three scripts from EP 2–4 work fine in isolation. But what if:
- Your machine crashes mid-run?
- You run the pipeline twice by accident?
- You add a new ticker — you want data for it, but don't want to re-fetch SPY's 3 years of history

Naive solution: delete everything and re-run. That works but is slow and wastes API quota. A real pipeline needs to know what it already has and only fetch what's new. That's what `incremental_runner.py` does.

### Checkpoint.json — How State Is Tracked (~4 min)
Show `checkpoint.json` before any run (empty or non-existent), then after a run:

```bash
# First run
python ingestion/incremental_runner.py --tickers SPY AAPL --start 2024-01-01

# Look at the checkpoint
cat data/checkpoint.json
```

Walk through the checkpoint structure:
- `last_run_at` — ISO timestamp of last successful complete run
- `tickers` — list of tickers tracked
- `ohlcv.last_date` — most recent date fetched per ticker
- `options.last_snapshot_date` — date of last options snapshot
- `status` — `completed` or `failed_at_step`

Now run it again immediately and show it skips everything:

```bash
python ingestion/incremental_runner.py --tickers SPY AAPL --start 2024-01-01
# Output: "All data up to date. Nothing to fetch."
```

### Simulating a Failure and Recovery (~4 min)
Edit `checkpoint.json` to set `status: "failed_at_step": "options"` — simulating a crash mid-run. Then re-run and show the pipeline picks up from the options step, not from the beginning:

```bash
# Edit checkpoint to simulate failure at options step
python -c "
import json, pathlib
cp = json.loads(pathlib.Path('data/checkpoint.json').read_text())
cp['status'] = {'failed_at_step': 'options'}
pathlib.Path('data/checkpoint.json').write_text(json.dumps(cp, indent=2))
"

# Re-run — watch it skip ohlcv and start from options
python ingestion/incremental_runner.py --tickers SPY AAPL --start 2024-01-01
```

### Adding a New Ticker (~3 min)
Add `NVDA` to the ticker list and run:

```bash
python ingestion/incremental_runner.py --tickers SPY AAPL NVDA --start 2024-01-01
```

Show that SPY and AAPL are skipped (already up to date) while NVDA gets the full backfill.

## The Code

```bash
# First full run
python ingestion/incremental_runner.py \
  --tickers SPY AAPL ^VIX NVDA QQQ \
  --start 2022-01-01 \
  --output-base-dir data/

# Subsequent runs (only fetches new data)
python ingestion/incremental_runner.py \
  --tickers SPY AAPL ^VIX NVDA QQQ \
  --start 2022-01-01 \
  --output-base-dir data/

# Check current state
cat data/checkpoint.json

# Force re-run a specific step (bypass checkpoint for options only)
python ingestion/incremental_runner.py \
  --tickers SPY AAPL \
  --start 2022-01-01 \
  --force-step options
```

## Key Concepts

**Idempotency**
A pipeline is idempotent if running it multiple times produces the same result as running it once. Without idempotency, double-runs produce duplicate data, partial writes, or silent corruption. `incremental_runner.py` achieves idempotency by checking the checkpoint before each step and skipping work that was already completed successfully.

**The checkpoint problem**
Any multi-step pipeline can fail between steps. If step 1 writes data and step 2 crashes, the next run needs to know: "step 1 is done, start from step 2." Without a checkpoint, you have two bad options: re-run everything (slow, wastes quota) or leave the pipeline half-done. Checkpoints make recovery deterministic.

**At-least-once vs exactly-once delivery**
Our pipeline is at-least-once: in some failure modes, a step might run twice (once before the crash, once during recovery). This is fine as long as steps are idempotent — writing the same Parquet file twice just overwrites it with identical data. Exactly-once delivery is much harder and not needed here.

**Cron vs event-driven scheduling**
Cron (time-based) is the right model for market data: pull at 6 PM ET every weekday. Event-driven (trigger on a webhook or message) would make sense if you were reacting to live market events — that's a different architecture (streaming vs batch). Batch is simpler, cheaper, and right for daily data.

## Common Gotchas

- **"checkpoint.json is missing and the run fails"** — The runner creates it on first run. If you delete it manually, the next run treats everything as new and re-fetches. That's intentional.
- **"I added a ticker but the runner still skips it"** — The checkpoint is keyed by ticker. Adding a new ticker means the checkpoint has no entry for it, so it will be fetched in full on the next run.
- **"Cron doesn't run on market holidays"** — Cron doesn't know about market calendars. The scripts handle this gracefully: yfinance returns no data for non-trading days, and the checkpoint advances the date anyway.
- **"Can I run this in parallel for multiple tickers?"** — The runner processes tickers sequentially to avoid rate-limiting yfinance and Alpaca. You can increase parallelism carefully, but the free tiers are strict.
