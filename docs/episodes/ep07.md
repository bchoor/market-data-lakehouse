## Episode Outline

### How iceberg_writer.py Works (~3 min)
Walk through the script at a high level without going line by line:
1. Reads Parquet files from the local source directory
2. Transforms them into the partitioned layout (ticker / year)
3. Uploads data files to R2 under the correct prefix
4. Creates a new Iceberg snapshot manifest pointing to the new files
5. Atomically swaps the metadata pointer to the new snapshot
6. Updates the Data Catalog entry

The atomic swap is the key Iceberg property — queries running during the write see a consistent snapshot (either fully old or fully new, never half-written).

Briefly show the time-travel concept (we'll use this more in EP 9):
```python
# In Python with PyIceberg
table.scan(snapshot_id=<old_snapshot_id>).to_pandas()
```

This is the "Bloomberg time machine" feature — you can rewind your data to any point in history. Useful for backtesting: "what did my data lake look like on January 3, 2024?"

## Key Concepts

**Iceberg snapshots (append-only)**
Every write to an Iceberg table creates a new snapshot. A snapshot is an immutable, consistent view of the table at a point in time. Old snapshots are not deleted (unless you run an explicit expire operation). This gives you: concurrent reads during writes (readers see the previous snapshot), time travel (query any past snapshot), and auditability (who wrote what, when). For a daily market data pipeline, you accumulate one new snapshot per daily run — totally manageable.

**Atomic snapshot commit**
The Iceberg write protocol is: (1) upload all data files, (2) write manifest files pointing to those data files, (3) write new metadata.json pointing to the new manifests, (4) atomically swap the catalog pointer to the new metadata.json. Step 4 is atomic — either it succeeds fully or the old snapshot remains. There is no partial state visible to readers.

**Partition pruning — why queries are fast**
A query `WHERE ticker = 'SPY' AND date >= '2024-01-01'` on a partitioned Iceberg table works like this: (1) read the manifest, (2) see that SPY data is only in `data/ticker=SPY/` partitions and 2024 data is only in `year=2024` partitions, (3) open only those files. If you have 5 years of data for 20 tickers but query only SPY 2024, the engine reads 1/100th of the total data. Without partitioning, every query scans everything.

**Append vs overwrite modes**
Append adds new files to a new snapshot without touching existing files. Overwrite replaces the entire table (deletes old snapshots, writes new). Use append for daily incremental runs. Use overwrite only for full historical reloads (e.g., after correcting a calculation error across all history).

## Common Gotchas

- **"Upload is slow for large datasets"** — R2 upload speed depends on your internet connection. For a 3-year full backfill of 10 tickers, expect 2–5 minutes on a normal connection. Incremental daily writes are seconds.
- **"I see data in R2 but the catalog shows no rows"** — The catalog only updates after the metadata swap (the final step). If the script crashed before that, the catalog is still pointing at the old snapshot. Re-run to retry — the write is idempotent as long as the source data hasn't changed.
- **"My R2 bucket is filling up with old metadata files"** — Iceberg retains metadata for every snapshot. Run `iceberg_writer.py --expire-snapshots --older-than 30d` to clean up old metadata. Data files referenced by unexpired snapshots are never deleted.
- **"ModuleNotFoundError: pyiceberg"** — Run `pip install -e .` again — pyiceberg is in the project dependencies and may not have installed if you set up before it was added.
