## Episode Outline

### Why Both DuckDB and R2 SQL? (~2 min)
You might wonder: if we already have R2 SQL, why add DuckDB? The answer is the development loop:

- **R2 SQL** — production queries. Runs in Cloudflare, callable via HTTP. Used by the MCP server (EP 10) and production dashboards.
- **DuckDB local** — development queries. No network calls, instant results, no cost, works offline. Used when writing new queries, debugging, or exploring data.

The key insight: both read the same Iceberg files in R2 using the same table format. Switching between them is a one-line change. Write your query in DuckDB, verify it, then point it at R2 SQL when you're ready for production.

### How DuckDB Reads Iceberg from R2 (~3 min)
DuckDB has a native Iceberg extension and an S3/R2 extension. When you run:
```python
duckdb.sql("SELECT * FROM iceberg_scan('s3://market-data-lakehouse/ohlcv')")
```
DuckDB:
1. Downloads the Iceberg metadata JSON from R2 (tiny file, ~2 KB)
2. Reads the manifest to find which Parquet files are needed for this query
3. Downloads only the relevant Parquet files (partition pruning applies here too)
4. Executes the query locally

The Parquet files themselves are cached locally after the first read, so subsequent queries on the same data are instant.

### Running duckdb_local.py (~5 min)
```bash
# Start an interactive DuckDB session with R2 Iceberg configured
python cloudflare/duckdb_local.py

# Or run a one-off query
python cloudflare/duckdb_local.py --sql "
  SELECT ticker, date, close, rsi_14
  FROM ohlcv
  WHERE rsi_14 < 30 AND date >= '2024-01-01'
  ORDER BY rsi_14 ASC
  LIMIT 10
"
```

Show both modes. In the interactive session, show tab-completion on table names and `.schema ohlcv` to inspect columns.

### Time Travel — Querying Past Snapshots (~2 min)
```python
# In duckdb_local.py interactive mode:
# Query the table as it looked at a specific snapshot
SELECT * FROM iceberg_scan(
  's3://market-data-lakehouse/ohlcv',
  snapshot_id = 1234567890
) LIMIT 5;

# List available snapshots
SELECT * FROM iceberg_snapshots('s3://market-data-lakehouse/ohlcv');
```

This is genuinely useful for backtesting: "what did my data look like on date X" — including any data corrections or additions that happened after that date.

## The Code

```bash
# Start interactive session
python cloudflare/duckdb_local.py

# Run a query directly
python cloudflare/duckdb_local.py --sql "SELECT COUNT(*) FROM ohlcv"

# Export query results to a local CSV
python cloudflare/duckdb_local.py \
  --sql "SELECT ticker, date, close, rsi_14 FROM ohlcv WHERE rsi_14 < 30 AND date >= '2024-01-01'" \
  --output results.csv

# Query without touching R2 (from local Parquet files)
python cloudflare/duckdb_local.py \
  --source local \
  --sql "SELECT ticker, COUNT(*) FROM ohlcv GROUP BY ticker"
```

Inside DuckDB interactive mode:
```sql
-- Check data freshness
SELECT MAX(date) as latest FROM ohlcv;

-- Options screener — find high-IV calls
SELECT
  symbol,
  expiration_date,
  strike_price,
  ROUND(implied_volatility * 100, 1) as iv_pct,
  ROUND(delta, 3) as delta,
  ROUND(theta, 3) as theta
FROM options_greeks
WHERE option_type = 'call'
  AND implied_volatility > 0.50
  AND delta BETWEEN 0.20 AND 0.40
  AND open_interest > 1000
ORDER BY implied_volatility DESC
LIMIT 20;

-- Correlation matrix (SPY vs sector ETFs over last 90 days)
SELECT
  a.ticker as ticker_a,
  b.ticker as ticker_b,
  ROUND(CORR(a.close, b.close), 3) as correlation
FROM ohlcv a
JOIN ohlcv b ON a.date = b.date
WHERE a.date >= CURRENT_DATE - INTERVAL 90 DAYS
  AND a.ticker IN ('SPY', 'QQQ', 'IWM', 'GLD', 'TLT')
  AND b.ticker IN ('SPY', 'QQQ', 'IWM', 'GLD', 'TLT')
GROUP BY a.ticker, b.ticker
ORDER BY a.ticker, b.ticker;
```

## Key Concepts

**DuckDB — the best local analytics tool for this stack**
DuckDB is an embedded analytical database — it runs in-process with Python, no server, no daemon. It's faster than pandas for aggregations on medium-to-large DataFrames, supports full SQL including window functions, reads Parquet natively, and has extensions for Iceberg and S3. For anyone building a market data stack, DuckDB replaces the need for local Postgres or SQLite for analytics.

**Local caching of R2 data**
DuckDB's S3 extension caches downloaded Parquet files locally (in `/tmp` by default, or a configurable path). The first query downloads the relevant partition files; subsequent queries read from cache. This means DuckDB + R2 Iceberg can work nearly offline after the first fetch of a partition — useful on a plane or in areas with poor connectivity.

**Iceberg time travel in DuckDB**
DuckDB's `iceberg_scan()` function accepts a `snapshot_id` parameter to read a historical snapshot. You can list all available snapshots with `iceberg_snapshots()`. This is useful for backtesting scenarios where you want to ensure your backtest used data that was actually available at a specific historical point — not data that was later corrected or added.

**The dev/prod parity principle**
Using the same table format (Iceberg) and nearly the same SQL dialect (DuckDB ≈ R2 SQL) means queries developed locally almost always work in production without changes. The only differences are connection details — the rest is identical. This is the same principle behind Docker for servers, applied to analytics.

## Common Gotchas

- **"DuckDB can't find the httpfs or iceberg extension"** — Run `INSTALL httpfs; LOAD httpfs; INSTALL iceberg; LOAD iceberg;` once in DuckDB. The `duckdb_local.py` script does this automatically, but the raw DuckDB CLI doesn't.
- **"Credentials error reading from R2"** — DuckDB's S3 extension needs to be configured with your R2 credentials. The `duckdb_local.py` script reads `.env` and sets these automatically. If you're using the raw DuckDB CLI, set them manually with `SET s3_access_key_id='...'` etc.
- **"First query is slow, subsequent ones are fast"** — Expected. First query downloads Parquet files from R2; they're cached for subsequent queries. The download is a one-time cost per partition.
- **"DuckDB results differ slightly from R2 SQL"** — Floating-point precision can differ slightly between DuckDB and Cloudflare's SQL engine for calculations involving large aggregations. For market data use cases, the differences are negligible (sub-cent on prices).
