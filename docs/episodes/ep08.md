## Episode Outline

### What R2 SQL Is (~2 min)
R2 SQL is a serverless SQL engine that Cloudflare runs on your behalf. You send an HTTP POST with a SQL string, and Cloudflare reads the Iceberg metadata, figures out which Parquet files to open, scans them, and returns results — all without any server you manage. It's the query layer that makes R2 + Iceberg a real database rather than just a folder of files.

### Exploring Your Lakehouse (~4 min)
```bash
# What tables do I have?
python cloudflare/r2sql_client.py --list-tables

# What columns does ohlcv have?
python cloudflare/r2sql_client.py --describe ohlcv

# What's the row count and date range?
python cloudflare/r2sql_client.py --sql "
  SELECT
    ticker,
    COUNT(*) as rows,
    MIN(date) as earliest,
    MAX(date) as latest
  FROM ohlcv
  GROUP BY ticker
  ORDER BY ticker
"
```

Run these live, show the output.

### The RSI Screener — Your First Real Query (~5 min)
This is the "wow" moment. You're querying your own market data lake from the cloud with plain SQL:

```bash
python cloudflare/r2sql_client.py --sql "
  SELECT
    ticker,
    date,
    close,
    volume,
    rsi_14,
    sma_20,
    atr_14
  FROM ohlcv
  WHERE rsi_14 < 30
    AND volume > 1000000
    AND date >= '2024-01-01'
  ORDER BY rsi_14 ASC
  LIMIT 20
"
```

Walk through the results:
- What does RSI < 30 mean (oversold signal)?
- Why filter volume > 1M (liquidity filter — avoid illiquid names)?
- What would a trader do with this list?

Then show a second query — identifying recent RSI crosses (RSI crossing up from below 30):
```bash
python cloudflare/r2sql_client.py --sql "
  SELECT
    ticker,
    date,
    close,
    rsi_14,
    LAG(rsi_14) OVER (PARTITION BY ticker ORDER BY date) as prev_rsi
  FROM ohlcv
  WHERE date >= '2024-06-01'
  QUALIFY prev_rsi < 30 AND rsi_14 >= 30
  ORDER BY date DESC
  LIMIT 20
"
```

### Understanding Query Execution (~4 min)
Explain what happens when R2 SQL runs a query:
1. Parse the SQL
2. Consult the Iceberg metadata to find relevant partitions
3. Download and scan only the needed Parquet files
4. Return results

Show why this matters: a full-table scan of 3 years of OHLCV for 20 tickers is ~10 million rows across ~100 Parquet files. A partitioned query for "just 2024" reads 1/3 of that. R2 SQL bills (on paid tiers) per byte scanned — efficient queries cost less.

## The Code

```bash
# List all registered tables
python cloudflare/r2sql_client.py --list-tables

# Describe schema
python cloudflare/r2sql_client.py --describe ohlcv
python cloudflare/r2sql_client.py --describe options_greeks

# RSI oversold screener
python cloudflare/r2sql_client.py --sql "
  SELECT ticker, date, close, volume, rsi_14
  FROM ohlcv
  WHERE rsi_14 < 30
    AND volume > 1000000
    AND date >= '2024-01-01'
  ORDER BY rsi_14 ASC
  LIMIT 20
"

# Volatility screener — high ATR names (big movers)
python cloudflare/r2sql_client.py --sql "
  SELECT ticker, date, close, atr_14,
         ROUND(atr_14 / close * 100, 2) as atr_pct
  FROM ohlcv
  WHERE date = (SELECT MAX(date) FROM ohlcv)
  ORDER BY atr_pct DESC
  LIMIT 15
"

# Bollinger Band squeeze — low volatility, potential breakout setup
python cloudflare/r2sql_client.py --sql "
  SELECT ticker, date, close,
         bb_upper - bb_lower as bb_width,
         ROUND((bb_upper - bb_lower) / bb_middle * 100, 2) as bb_width_pct
  FROM ohlcv
  WHERE date = (SELECT MAX(date) FROM ohlcv)
    AND volume > 500000
  ORDER BY bb_width_pct ASC
  LIMIT 20
"
```

## Key Concepts

**Serverless SQL — no cluster, no always-on cost**
Traditional SQL databases (Postgres, MySQL) run a server you pay for 24/7. R2 SQL is pay-per-query — you pay only when you run a query, and the free tier covers a meaningful amount of usage for personal/small-fund use. There's no cluster to size, scale, or maintain.

**QUALIFY clause (DuckDB/Trino syntax)**
`QUALIFY` filters window function results — it's like `WHERE` but for window functions like `LAG()`. Standard SQL doesn't have `QUALIFY`; it's a DuckDB/Trino/Snowflake extension. R2 SQL is compatible with this syntax. The alternative is wrapping in a subquery, which is uglier.

**Partition pruning in queries**
Every `WHERE date >= '2024-01-01'` clause triggers partition pruning — R2 SQL reads the Iceberg partition spec, determines that data before 2024 is in different partition files, and skips those files entirely. No data outside 2024 is ever downloaded. Always include date filters in your queries when you only need recent data.

**RSI as a mean-reversion signal**
RSI (Relative Strength Index) ranges from 0 to 100. Below 30 is conventionally "oversold" — the stock has fallen fast and may bounce. Above 70 is "overbought." These are not reliable signals on their own — but combined with volume confirmation and support/resistance context, they're a useful starting filter for deeper analysis.

## Common Gotchas

- **"SQL errors about table not found"** — R2 SQL uses the catalog namespace. Make sure your table name matches what was registered in EP 6: `ohlcv` not `market_data.ohlcv` (the client sets the namespace automatically, but check if it errors).
- **"Query times out"** — Full-table scans on large datasets can be slow on the free tier. Add date filters and ticker filters to your queries. `WHERE date >= '2024-01-01' AND ticker IN ('SPY', 'AAPL')` is dramatically faster than a full scan.
- **"Results come back as strings, not numbers"** — The CLI client returns JSON by default. The Python client (`r2sql_client.py --format pandas`) returns a proper DataFrame with correct types.
- **"I don't see the QUALIFY keyword in docs"** — R2 SQL's SQL dialect is compatible with DuckDB. If Cloudflare docs don't mention a feature, check DuckDB docs — most DuckDB SQL extensions work.
