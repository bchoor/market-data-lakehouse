### Inspecting the Output with DuckDB (~5 min)
Fire up DuckDB to peek at what was written:

```bash
# Open DuckDB CLI
duckdb

# In DuckDB:
-- See all files written
SELECT * FROM glob('data/ohlcv/**/*.parquet');

-- Peek at schema and first rows
DESCRIBE SELECT * FROM read_parquet('data/ohlcv/**/*.parquet');
SELECT ticker, date, open, high, low, close, volume, rsi_14, sma_20
FROM read_parquet('data/ohlcv/**/*.parquet')
WHERE ticker = 'SPY'
ORDER BY date DESC
LIMIT 10;

-- Check RSI distribution
SELECT
  ticker,
  COUNT(*) as days,
  ROUND(AVG(rsi_14), 1) as avg_rsi,
  MIN(rsi_14) as min_rsi,
  MAX(rsi_14) as max_rsi
FROM read_parquet('data/ohlcv/**/*.parquet')
GROUP BY ticker;
```

### Understanding the Output Schema (~2 min)
Walk through each column:
- `ticker`, `date` — primary keys
- `open`, `high`, `low`, `close`, `volume` — raw OHLCV from Yahoo
- `adj_close` — adjusted for splits/dividends (use this for backtesting returns)
- `sma_20`, `sma_50`, `ema_12`, `ema_26` — moving averages
- `rsi_14` — Relative Strength Index (14-day), range 0–100
- `bb_upper`, `bb_middle`, `bb_lower` — Bollinger Bands (20-day, 2σ)
- `macd`, `macd_signal`, `macd_hist` — MACD components
- `atr_14` — Average True Range (volatility proxy)

## Key Concepts

**Pre-computing indicators at ingest time**
We calculate RSI, SMA, ATR, etc. once during backfill and store the results in the Parquet file. The alternative is computing them at query time (e.g., inside a SQL window function). Pre-computing is better for this stack because: (1) R2 SQL is serverless — you pay per byte scanned, not per CPU cycle; (2) indicator math is stateful across rows and awkward in SQL; (3) your screener queries stay simple (`WHERE rsi_14 < 30` is cleaner than a 20-line window function).

**Parquet and columnar storage**
Parquet stores data column by column rather than row by row. When you run `SELECT close, rsi_14 FROM ohlcv`, Parquet only reads those two columns from disk — it skips `volume`, `bb_upper`, and everything else. For wide tables with many indicators, this makes queries 5–20x faster than CSV.

**^VIX — why it's in your dataset**
VIX is the CBOE Volatility Index — the market's implied volatility for S&P 500 options over the next 30 days. Traders use it as a fear gauge. A VIX above 30 means the market is panicking. Tracking VIX alongside your equity prices lets you filter signals by volatility regime: "only take mean-reversion trades when VIX < 20."

**Adjusted close vs close**
Yahoo Finance returns both `close` (unadjusted) and `adj_close` (adjusted for splits and dividends). For backtesting, always use `adj_close`. A 4-for-1 stock split makes raw `close` look like the price dropped 75% overnight — your backtest will be wrong.

## Common Gotchas

- **"yfinance throws an exception for ^VIX"** — Use the caret (`^VIX`), not `VIX`. The caret tells Yahoo it's an index, not a stock.
- **"The RSI is NaN for the first 14 rows"** — Correct. RSI needs 14 days of history to compute. The script leaves those NaN rather than backfilling with a wrong value.
- **"The Parquet files are huge"** — They're not. 3 years of daily data for 10 tickers is ~5 MB total. Parquet compresses extremely well.
- **"My date range returns fewer rows than expected"** — Yahoo Finance doesn't have data for weekends and market holidays. A full year has ~252 trading days, not 365.
